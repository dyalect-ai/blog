EvaluationFrom general judges to specified cases

Decide what good means before the run, not while grading it.

Many teams test an AI system with a judge model that reads the whole run and gives a score. It is quick to set up and good at finding failures. But the score can move for no reason anyone can name, an average hides the one thing that went wrong, and you cannot approve a release or train a model on it. A mature evaluation writes down what good means before the run, checks what the system actually left behind, asks a judge one narrow question at a time, and measures that judge against people. This post sets out the two stages, grades one case both ways, and ends with six questions to place your own team.

00Overview

Most teams that test an AI system today do it with a judgeZheng et al., 2023: another model reads the whole run, works out what success means, and gives a score. The score moves from 0.87 to 0.81 and nobody can say why. Did the system get worse, or did the judge read it differently?

A more mature evaluation moves that decision. It writes down what a good result is before the run, inside each test case, so grading only has to check (Figure 1). The system runs for real from a known starting state. Code checks what it left behind. A judge answers one narrow yes/no question at a time, and only after it has been measured against people.

We call the two ways stage 1, general judges, and stage 2, specified cases. Stage 1 is a sensible place to start and the right tool for two jobs: finding out how a new system fails, and watching live traffic. It is not a sound basis for approving a release, and its score should never be the reward a model is trained on. Below: why, what stage 2 looks like on one worked case, and six questions that tell you which stage you are in.

01How most teams evaluate today

A stage 1 evaluation has a handful of example requests, tools that are simulated, and general judges that each read the whole transcript and answer a broad question: was the task completed, was anything made up, was anything unsafe. The scores are averaged and compared with a pass mark. It is quick to set up, takes almost no work per example, and runs on anything, including live traffic. Many teams are still here when they start making release decisions on the number, and that is when seven problems show up.

  1. Nobody wrote down what should happen. Ask a judge whether a digest of follow-ups is complete and it must decide, run by run, what complete means. Its idea may differ from yours and from its own next idea.
  2. It grades what was said, not what was done. “Done. I’ve created the task” can sit beside zero new tasks in the system. With simulated tools no task could exist, so there is nothing to look at.
  3. Big questions get unstable answers. A broad question over a long answer leaves a judge room to disagree with experts, and with itself: the same bundled question asked twice can change its answer.
  4. The judge reads everything. Models use the middle of a long input less well than its start and endLiu et al., 2023, so a judge misses what is there, and a confident “all done” sways it.
  5. A score hides the failure. Four things right and one overlooked restriction scores 0.8. Averaged with other runs it clears the pass mark.
  6. Nobody has measured the judge. Reviewing verdicts you can already see mostly confirms them and never finds what the judge waved through.
  7. A bad number does not say what to fix. “Task completion fell from 0.87 to 0.81” names no behaviour. Somebody has to read transcripts to find out.

Put together, the number moves and you cannot tell whether the system changed or the judge read it differently. That is fine for exploring, but not for approving a release. The same run can pass as a score and fail as a check (Figure 2).

02What stage 2 looks like

In a stage 2 evaluation every case says what a pass is before anything runs. A case has eight parts, and they split into what the system is given, what the run must leave behind, and what the output must say.

PartWhat it holdsChecked by
Starting stateEverything the system can see or reach, seeded from synthetic data with the clock fixed—
RequestWhat the user asks, worded as a user would, with no hint of the traps—
Must be true afterwardsThe records, files or messages that must existCode
May changeWhat may change without failing the run. Nothing else mayCode
May do, must doThe tools allowed, and the actions needed for the result to be trustedCode
Wanted rowsYes/no questions about features the output must haveA judge
Unwanted rowsYes/no questions about features the output must not have, each with a planted trapA judge
Evidence for each rowWhat is needed to answer that row and nothing more—

Take one case from start to finish. A support assistant is asked to review the user’s recent account reviews and write a digest of required and overdue follow-ups. Four reviews are seeded, with traps planted on purpose. The system runs for real against them (Figure 3).

The grading rests on three choices. Code decides everything code can decide: counts, exact values, which tools were used, what changed. It gives the same answer every time at no cost. A judge answers one row per call: one yes/no question about one fact, shown only the evidence that question needs. A run passes only if every check passes. There is no partial credit and no weighted average, and the verdict is one of three: PASS, FAIL with the name of the check that failed, or ERROR, meaning it could not be graded. An error is never a pass, and a run in which nothing was checked is never a pass.

Small questions, small evidence

In stage 1 a judge is given one big question and everything as evidence: the whole conversation, every tool call, all four notes. In stage 2 the question “does the reply include the escalation to the payments team?” is shown the reply and the note for review A, and nothing else. There is no confident “all done” in view to sway it, and less to overlook. Any single verdict can be checked by an expert in under a minute.

Because a person can check a verdict that fast, the judge itself can be measured. People answer a sample of the same rows, on the same evidence, without seeing the judge’s answer. If they agree with the judge as well as they agree with each other, the judge is trusted to gate. If not, the disagreement is a row to look at, not a number to average away.

04Pitfalls

The half move

Adopting the format of stage 2 is not the same as getting there. Yes/no questions instead of scores and a pass/fail verdict are the visible part. If the tools are still simulated and the judges still read everything, you have the blind spots of stage 1 with the look of stage 2. The test is the four questions below the first row, and all four must be yes.

Most bad rows are bad in one of eight ways

The faultExampleThe fix
Two facts in one row. If one is missing, the honest answer is neither yes nor no. These rows flip most between reruns.“Does the reply cover the usage report and the payments escalation?”Split at every “and”.
Vague words. There is no boundary, so every reader draws their own.“Does it handle the upgrade appropriately?”Name the fact: “Does the reply recommend upgrading the plan now?”
Conditional rows. Leaving the fact out passes.“If the summary mentions the credit, is it $50?”Ask for the fact: “Does it record a $50 credit?”
Rows that need the whole run. A broad question in disguise.“Did it use the notes correctly?”Break it down. One row per fact, each with the reply and one note.
Exact wording. A correct paraphrase fails.“Does it say ‘re-run the usage report in 3 months’?”Name the fact and what counts: 12 weeks counts.
Facts the system could not know. Guessing is rewarded and honesty punished.“Does it give the date of the next call?” when the data holds noneA row exists only if the starting state establishes the fact.
Must-not rows with no temptation. They pass trivially and prove nothing.“Does it recommend a US region?” when nothing invites onePlant a trap: a contract that forbids US regions, beside a need for a region.
A judge where code would do. You pay for noise you did not need.“Was exactly one chat created?”Give it to code.

Two habits help. Say what failure looks like: a row that states both the passing and the failing condition, and names absence explicitly, is applied more consistently, because a judge that is not told to look for something missing tends to look only for something wrong. And fix the row before you tune the judge: unstable verdicts concentrate in a few faulty rows, and rows that hold two facts are the largest source of flips.

Seven ways to get a number that means nothing

The shortcutWhat goes wrongInstead
Only testing what must not happenA system that refuses everything passes.Include cases where helping is right. Use wanted and unwanted rows together.
Showing reviewers the judge’s verdictThey agree with it.Blind review: the same question, the same evidence, no verdict.
Counting errors as passesA grader that crashed looks like a perfect system.An error is never a pass. A run with nothing checked is never a pass.
One run per caseModels vary between attempts, so one pass can be luck.Run each case several times.
Tuning on the cases you reportThe number climbs and the system does not.Keep some cases held out, and confirm on cases you have not looked at.
Softening a case until the system passesThe evaluation stops measuring anything.Change a case only when the case is wrong, and record why.
Starting with the whole benchmarkIt is too broad to specify, and its pass rate means nothing in particular.One capability, one sentence, one set of cases. Combine sets later.

When a run fails, decide first which was at fault, the system or the case. Fix the system to pass the case. Fix the case only when the case was wrong.

05Reading the result

One attempt passing is not the same as every attempt passing. Run each case several times and report both numbers. pass@1 is how often a single attempt passes. pass^kYao et al., 2024 is how often k attempts all pass: for a case with n runs of which c passed, the chance that k runs drawn from the n all passed. The gap between the first and the last is the unreliability (Figure 4).

Two more things belong beside the number. Give an interval, because with twenty cases and a pass rate near half the interval is roughly twenty points either side, and a difference inside it is not a difference. And break failures down by check, so the result says what failed, not only that something did.

The new number will also be lower than the stage 1 score it replaces, and the two are not comparable. A lenient score of 0.83 judged afterwards and a strict pass rate where every check must pass are different rulers. The system has not got worse; the test is stricter. Say so when you publish the first number.

06Three kinds of judge reliability, and what may train a model

There is no single “judge reliability” number. Three different things are measured, and each answers a different question. Name which one you mean (Figure 5).

This matters most when a score is about to become a training reward. A model trained on a noisy judge learns the judge’s quirks. A stage 1 score is for discovery and monitoring and is never a reward.

Before a score trains a model, or backs the claim that a trained model is better

  • It is stage 2: all four questions in section 04 are yes.
  • It repeats: rerun, it stays within a bar fixed before training started.
  • People agree with it: it has been checked against blind labels.
  • It leaves room to learn: not nearly all passing, not nearly all failing.

Until all four hold, label the number “judge not yet validated against people” and do not train on it.

07What to do

Find where you are

Six questions about your evaluation today. Mostly no means stage 1. Mixed is likely the half move. All yes is stage 2.

  1. Could a new colleague read one case and say exactly what a passing result is, without running anything?
  2. Does grading inspect what changed (records, files, messages sent) or only the transcript?
  3. Are the system’s tools and dependencies real in the evaluation?
  4. Can a domain expert answer each judge question yes or no in under a minute, from the evidence the judge gets?
  5. When a run fails, does the result name the specific thing that went wrong?
  6. Do you know how often your judge disagrees with experts, and with itself on a rerun?

Stage 1 still has its uses. Each stage fits different jobs:

The jobStage 1Stage 2Why
Finding how a new system failsYesNot yetNo definition of correct exists yet. The failures the judges flag become your first cases.
Watching live trafficYesNoLive traffic has no case specification. Check the general judge with the expert labels from stage 2.
Approving a release, catching a regressionNoYesA score can move without a reason. A failed check names one.
A training rewardNeverOnce measuredOnly when the four conditions in section 06 hold.

Move to stage 2 when you cannot explain a change in the score, when reviewers keep disagreeing with the judges, when a regression ships that the evaluation passed, or when the evaluation is about to decide releases.

Then grow the set, one capability at a time, and combine sets later. Keep about a quarter of the cases held out and look at them only to report. Add a case whenever real use shows a failure the set did not catch, and when nearly every case passes every attempt, write harder ones.

What it costs, and what it does not solve

Each case takes real authoring work and a domain expert to review it. You need an environment where the real system runs on seeded data, and expert time for blind labelling. It works on fixed cases only, so live traffic still needs general judges. And pass or fail treats a missed escalation and an unsafe recommendation alike, unless you tag rows by severity and report the severe ones separately.

Ten rules

For an evaluation you can make release decisions on

  1. Write down the expected result before the run. One set of cases tests one capability.
  2. Run the real system against real dependencies, from a known starting state.
  3. Check what changed, not what was claimed.
  4. Let code decide everything code can decide.
  5. Ask a judge one yes/no question about one fact.
  6. Give the judge only the evidence that question needs. If it needs the whole run, rewrite the question.
  7. Test for what must be there and what must not. Plant a temptation for every must-not.
  8. A run passes only if every check passes. An error is not a pass.
  9. Measure the judge against people who cannot see its answers, and against itself on a rerun.
  10. Run each case several times. Report one-attempt and every-attempt pass rates with the versions behind them.
